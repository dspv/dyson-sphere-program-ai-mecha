# AI-Native Game-Agent Research

**As of 2026-09-24.** This document owns the external-agent comparison and the proposed DSP experiment. It is a research direction, not a claim that autonomous play or model learning has occurred. [Build status](../.ai/14-build-status.md) owns actual results; [reward policy](REWARD-LEARNING.md) owns scoring.

## What existing projects demonstrate

- **[Voyager](https://arxiv.org/abs/2305.16291) ([code](https://github.com/MineDojo/Voyager))** uses an automatic curriculum, environment feedback, self-verification, and a retrievable library of executable skills in Minecraft. This is a useful pattern for an agent that chooses its own next achievable goal. Its skill memory is not neural-weight training, and Minecraft results do not establish DSP performance.
- **[Factorio Learning Environment](https://arxiv.org/abs/2503.09617) ([code](https://github.com/JackHopkins/factorio-learning-environment))** exposes a programmatic action/observation loop and separates open play from fixed laboratory tasks. Its paper reports that even strong language models struggle with spatial reasoning and complex automation. This supports a DSP test harness with short, inspectable action feedback and both open-ended play and repeatable checkpoint evaluations; it does not imply that a Factorio agent can directly operate DSP.
- **[Cradle](https://github.com/BAAI-Agents/Cradle) ([new-game porting guide](https://github.com/BAAI-Agents/Cradle/blob/main/docs/envs/new_game.md))** controls games from screenshots with mouse and keyboard and adds game-specific atomic skills and reflection. It offers a visual fallback, but its own porting guide requires per-game controls. The earlier DSP UI construction trial showed why screen-only placement is slow to verify and difficult to replay precisely. That is a local observation, not a published Cradle benchmark in DSP.
- **[Spherewright 0.3.3](https://thunderstore.io/c/dyson-sphere-program/p/Arcueid_77/Spherewright/) ([source](https://github.com/AvaloNero/Spherewright))** is the closest DSP-specific action bridge: its released package advertises structured observation and normal-mechanics actions, including creating a new ordinary world. Its published compatibility is DSP `0.10.34.28529` with BepInEx `5.4.17`, so it has not been installed in this project's `0.10.35.29088` game. The upstream repository describes unreleased 0.4 development features; those are research leads, not capabilities of the 0.3.3 package or this bridge. Spherewright describes itself as a bridge, not a self-directed goal learner.

No reviewed project demonstrates a self-directed agent finishing DSP on this installed build. The strongest transferable idea is a **model-directed experimental loop over bounded game tools**, with measurements rather than narration deciding whether an attempted skill worked.

## Proposed DSP learning loop

The model owns the next goal, its reason for choosing it, a predicted observable result, and one bounded attempt. It may choose exploration, gathering, research, construction, diagnosis, or recovery according to current capabilities and the long-term white-matrix objective. A goal can be rejected as infeasible by observed game prerequisites; the bridge does not prescribe a fixed campaign or silently substitute a scripted factory plan. The model may call an existing verified skill, compose skills, or propose a new experiment. Each experiment ends with a fresh observation and a verifier decision: achieved, failed, partial, or unknown. A failure becomes a counterexample with its blocker and changed hypothesis, not an invitation to repeat the same timed-out action.

The bridge owns legality and bounded execution on the game thread: ordinary game costs, reachable placement, session and planet checks, cancellation, operation identity, and truthful partial results. It should expose small actions and precise inspection, not arbitrary pool writes or unrestricted generated C# inside DSP. Screenshot/UI observations remain available where an in-game API has not been verified. The episode journal stores goal, prediction, action, before/after observations, visible UI evidence, elapsed game ticks, and outcome outside Git. Only a skill that worked and can be rechecked is eligible for reuse. The SQLite strategy memory is currently an **offline comparison mechanism**, not a trained gameplay policy.

## Strategy, tactics, and experiment contract

The model maintains a revisable strategic objective, a near-term goal, and one tactical experiment. At each decision it records why the goal is feasible from current observations, which prerequisite it serves, what result it predicts, and what observation would falsify that prediction. It may retain, revise, suspend, or abandon a goal after feedback. The long-term white-matrix objective supplies direction and an external outcome measure; it does not prescribe the next task or a fixed build order.

An experiment consists of a before snapshot, one bounded tool action or a read-only investigation, an operation identity, an after snapshot, and a verifier result. The verifier can report achieved, failed, partial, or unknown. A result records both the observed difference and the proposed explanation; a proposed explanation remains a hypothesis until supported by later evidence. Repeating an identical failed action without a changed hypothesis or game state is disallowed. Session changes and interrupted actions require reconciliation before another mutation.

Memory keeps successful skills and counterexamples with the goal, prerequisites, game version, save context, action sequence, evidence references, outcome, and known applicability limits. Retrieval ranks memories by observed context and gives the model both successful examples and relevant failures. A retrieved skill is a candidate plan, not an unconditional command. The agent must check its preconditions in the current game and verify its result again. An unverified model narrative cannot become a reusable skill.

The offline `experiments.py` ledger persists goal and experiment fields and blocks unresolved or identical failed retries. It now stores a compact observed context and ranks same-goal memories by simple applicability signals; the version filter is only as precise as the bridge's coarse `0.10.35` report. `experiment_runner.py` can conduct one budgeted attempt using injected goal, plan, observation, action, and verifier providers. `responses_experiment.py` implements structured model proposals for goals and inspect/walk/mine experiments, checked only against fake HTTP responses. The bridge adapter and primitive verifier are wired under fake bridge tests, but no live model call or runner-issued DSP action has occurred. The next gates are a copied-save live trial of this exact path, goal-specific verification of predictions, visible UI comparison, a construction action, and measured skill-transfer trials. It should allow the model to choose among currently verified tools without silently replacing its decisions with a handcrafted factory script. Matched checkpoint trials with memory enabled and disabled, followed by a different seed, will test whether recall actually improves decisions. Until those trials exist, the implementation is infrastructure for learning, not evidence that learning occurred.

This is AI-native because the model decides **what to try and how to revise its approach**. Deterministic code protects the game and measures outcomes; it does not choose the agent's entire progression route. If later work seeks neural-weight updates or reinforcement learning, that is a separate experiment requiring a dataset, training method, held-out saves, and evidence that the updated model outperforms the same model without training. Prompt revision, retrieved episodes, and strategy promotion must not be called weight training.

## What must be built, and what the bridge alone can do

A model-independent interface should expose the same typed observation and action schema to any compatible provider. The bridge is its game adapter: it makes DSP observable and controllable, but it has no persistent policy or automatic weight update. An external experiment runner must manage a hierarchy of revisable objectives: a long-horizon intention, the next feasible subgoal, and one immediate action. At each observation, the model can keep, revise, suspend, or abandon those objectives and explain what game evidence changed its decision. The runner bounds time and calls, persists private episodes, retrieves relevant verified skills and counterexamples, and gives the model its own previous prediction alongside the actual result. A verifier decides whether a claimed capability was demonstrated; the model does not award itself success.

This supports **in-context adaptation and skill-memory learning** first. The agent can improve across episodes without modifying model weights by remembering which experiments worked, composing skills, and avoiding known failures. Actual weight training would require an explicit training pipeline, sufficient varied trajectories, a separately held-out evaluation set, and comparison against the unchanged base model. We should implement and measure the game loop before deciding whether weight training adds value. The design must permit another model to enter the same checkpoint and action environment without rewriting DSP tools or inheriting hidden game-specific instructions.

## First falsifiable experiment

1. Start from two byte-identical copies of a pristine ordinary new-game checkpoint. Preserve the original. Configure a bounded game-time and tool-call budget before the run; record it in each private episode. Allow the model to see only verified observations and choose a short feasible goal itself. Do not provide the iron-line action sequence as a hidden script.
2. Run a baseline with the same model and action tools but without retrieval of prior successful skills. Record each prediction, action, game tick, visible result, failure, and idle interval. The model must remain free to choose goals within the ordinary-game rules.
3. On a matched copy, enable retrieval of verified episode lessons and compare the changed strategy under the configured paired-trial rule. Repeat on another checkpoint or seed to test transfer. The comparison must report completed verified capabilities, downstream throughput, action count, elapsed game ticks, failed repeats, and idle time; a merely larger inventory is not progress.
4. Treat sustained, attributed production as stronger evidence than placement or manually gathered items. Use the exact entity counter only for the checked recipe/version/identity and UI-supported input flow. The [reward policy](REWARD-LEARNING.md) keeps white-matrix throughput primary and intermediate points bounded.

The near-term engineering blocker is the **action surface**. This bridge can observe, walk, and mine, but it cannot yet perform ordinary construction through a bounded game command. A model-only change cannot make a miner, belt, sorter, power connection, and smelter appear in a reproducible new-game trial. The next integration slice is a small, previewable, normal-mechanics construction action with readback, cancellation, and restart reconciliation, followed by an actual model-chosen episode. Until that exists, visual computer control is a possible research branch, not a claim of autonomous construction.
