## Verified source findings

- The [BepInEx 5 plugin documentation](https://docs.bepinex.dev/v5.4.16/api/BepInEx.BaseUnityPlugin.html) defines `BaseUnityPlugin` and its logger/config surface. The [setup guide](https://docs.bepinex.dev/v5.4.11/articles/dev_guide/plugin_tutorial/1_setup.html) says to select .NET target from managed runtime DLLs; do not assume a target for the owner's game.
- The [BepInEx install guide](https://docs.bepinex.dev/master/articles/user_guide/installation/) distinguishes Mono and IL2CPP builds. Choose the distribution after inspecting the game installation.
- The [DSP_Mod repository](https://github.com/starfi5h/DSP_Mod) contains BuildToolOpt and documents local game DLL references, a publicized `Assembly-CSharp` for its own development setup, and MIT licensing. Its approach is a lead, not a signature guarantee for this game version.
- [BlueprintTweaks source](https://github.com/kremnev8/DSP-Mods/tree/master/Mods/BlueprintTweaks) is a candidate for studying blueprint and placement paths. Its present compatibility and license for any borrowed code need direct verification before reuse.
- The [blueprint generator](https://github.com/RasmusStagsted/dsp_bp_generator) is only a format lead; the source specification warns that its format may be outdated.

Source review of pinned revisions found:

- [BuildToolOpt revision `be56c083`](https://github.com/starfi5h/DSP_Mod/tree/be56c08309d708dcd3f80fc03b2f36f5cc124459/BuildToolOpt) targets `net472` in its project file and references local game assemblies. It patches `BuildTool_Click`, `BuildTool_Inserter`, path/addon tools, and blueprint paste. - [Spherewright revision `27082109`](https://github.com/AvaloNero/Spherewright/tree/270821096137ddf4fc69c36126c9a7d9b1a66e74) is an MIT-licensed, separate BepInEx/MCP project close to this project's intended bridge. Its reported gameplay tests are upstream claims, not tests in the owner's game. The 0.4 source has an unshipped read-only factory planner; the released package must not be assumed to have that feature.

1. Record game version, executable path, architecture, scripting backend, and the presence of `DSPGAME_Data/Managed/Assembly-CSharp.dll`, `mscorlib.dll`, and `netstandard.dll`.
2. Install a matching BepInEx build, launch the game once, record its version and startup log, and locate `BepInEx/core` and `BepInEx/LogOutput.log`.
3. Build only against local DLLs. Record hashes and versions in the private run log; do not commit DLLs.
4. Inspect actual `GameMain`, player, factory, inventory, and build-tool signatures in this version. For every candidate method, record assembly/type/method, thread context, prerequisites, error behavior, and one visible game check.
5. Study the current BuildToolOpt and BlueprintTweaks code for normal build previews, placement errors, construction drones, belts, sorters, and recipes. Record license before borrowing any code.
6. Complete one observation before attempting a mutation. Preserve the original save and use a copy for every experiment.

## Version-specific API record

The following signatures were decompiled from this installation's `DSPGAME_Data/Managed/Assembly-CSharp.dll` with ILSpyCmd 9.1.0.7988 and compiled against that DLL. All reads are made from `Plugin.Update()` on Unity's game thread. A responsive main-menu call with the first observer candidate initially returned a false `ok`: the menu demo had a running tick, `GameData`, and populated inventory. The observer now requires a non-demo game, tick greater than zero, a local planet, and a player on that planet. A responsive menu returned `status=not_loaded` and a null session. The arrival animation also returned `not_loaded` until landing completed.

- **Version/session:** `GameConfig.gameVersion : System.Version`, `GameConfig.build : int`, `GameMain.data : GameData`, `GameMain.isRunning : bool`, `GameMain.gameName : string`, `GameMain.gameTick : long`, `GameMain.isPaused : bool`, `GameMain.mainPlayer : Player`, `DSPGame.IsMenuDemo : bool`, and `GameMain.instance.isMenuDemo : bool`. The bridge creates a new random session ID when a ready `GameData` object appears. The observer's `embedded_save_name` is `GameMain.gameName`; it is **not** the loaded filename. `GameSave.LoadCurrentGame(string saveName)` sets `GameMain.data.gameName` from the filename only inside its `AllowRecursive` branch. Loading a byte-for-byte copy named `0-DSP-AI-33434023-Experiment-A.dsv` still reported the embedded `DSP-AI-33434023-Pristine`. The observer therefore reports `loaded_file_name=null`; action guards must not rely on this label. `GameConfig.build` was zero in both menu and game, so the full build is unknown through this API.
- **Planet and position:** `GameMain.localPlanet : PlanetData`, `PlanetData.id : int`, `PlanetData.displayName : string`, `Player.planetId : int`, `Player.position : UnityEngine.Vector3`, and `Maths.GetLatitudeLongitude(Vector3 pos, out int latd, out int latf, out int logd, out int logf, out bool north, out bool south, out bool west, out bool east) : void`. On the copied ordinary seed `33434023` save, the observer reported `Ancha II` and `1°37′ S, 115°35′ E`, exactly matching the visible planet name and coordinate display. The underlying vector was approximately `(181.77948, -5.71299, 87.05093)`; the visible UI offers geographic coordinates, so the vector is corroborated through the same installed conversion method, not directly displayed.
- **Inventory:** `Player.package : StorageComponent`, `StorageComponent.size : int`, `StorageComponent.grids : StorageComponent.GRID[]`, and `GRID.itemId/count : int`. The observer sums positive counts over at most 256 slots and marks incomplete scans. The new copied save returned 40 slots, complete, and no items; the open inventory UI was empty. A second copied ordinary save returned 50 slots and `item_id=2001,count=2132`; its inventory UI showed seven stacks of 300 Mk.I conveyor belts plus one stack of 32.

The observer scans at most 4096 pool indices, returns at most 64 positive-ID entities within 25 game coordinate units of `Player.position`, and signals truncation. The new game's factory pool had no built entities, matching the visible world; the landing capsule is not a factory entity. The second copied save returned nearby `proto_id=2001` entities in an area visibly filled with Mk.I conveyor belts; hovering one showed `Conveyor Belt Mk.I`. Its pool exceeded 4096 entries and more than 64 were nearby, so `complete=false` and `result_truncated=true`. This is a bounded partial answer, not an exhaustive local inventory.
- **Local veins:** `PlanetFactory.veinCursor : int`, `PlanetFactory.veinPool : VeinData[]`, and `VeinData.id/type/productId/amount/pos`. The same 4096-index, 64-result, radius-25 cap applies. The other six nearby `type=2`, `productId=1002` nodes have not yet been visually checked.
