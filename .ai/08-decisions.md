# Architecture Decision Records

Accepted decisions remain here even when superseded. Each entry says what was chosen, excluded, and what would reopen it.

## ADR-001 — Ordinary visible gameplay is the acceptance environment

**Date:** 2026-09-23. **Source:** specification. **Status:** accepted.

The first demo must use a prepared ordinary save with Dark Fog disabled, and later autonomous progression must use a new ordinary save. Visible game state and measured production are the proof. This keeps the experiment about gameplay rather than save manipulation.

**Rules out:** Sandbox-only acceptance, direct pool or save mutations, injected resources, invisible simulation.

**Revisit if:** The user changes the goal and explicitly accepts a different experiment.

## ADR-002 — Separate model planning from deterministic execution

**Date:** 2026-09-23. **Source:** specification. **Status:** accepted.

A local agent chooses bounded skills; deterministic bridge code validates and executes placement using verified game mechanics. This limits model errors and gives repeatable, inspectable failures.

**Rules out:** High-frequency model-driven key presses and arbitrary C# generated by the model inside the game.

**Revisit if:** A tested game API makes a different bounded, auditable control surface safer.

## ADR-003 — Start with loopback HTTP and versioned JSON

**Date:** 2026-09-23. **Source:** developer choice. **Status:** provisional.

Loopback HTTP is easy to inspect from Windows and the macOS development environment. A fixed JSON envelope permits contract tests before gameplay. Binding and request limits are required before execution is exposed.

**Rules out:** Remote listening and an unversioned ad hoc protocol. Named pipes remain an alternative.

**Revisit if:** The installed Unity/Mono runtime does not reliably support the chosen listener or HTTP introduces measurable game-thread stalls.

## ADR-004 — Treat game method signatures as unverified until the installed build is inspected

**Date:** 2026-09-23. **Source:** developer choice from the specification's research requirement. **Status:** accepted.

Open-source mods are useful leads, but game versions change. A method name copied from a repository cannot establish compatibility with the owner's game. The first bridge should not perform a mutation based on an unverified signature.

**Rules out:** Claiming game integration from source review, compiling against redistributed game DLLs, and coding placement from one old article.

**Revisit if:** A pinned game build and a maintained, verified API dependency supply equivalent evidence.

## ADR-005 — Use an external agent process with local-only episode data

**Date:** 2026-09-23. **Source:** specification. **Status:** accepted.

The OpenAI key, journal, budgets, and strategy experiments live outside the game. Raw episodes and saves remain local by default because they can contain private save details.

**Rules out:** Placing API credentials in BepInEx config and committing raw save or episode data.

**Revisit if:** A different secret store and privacy model are explicitly approved and documented.

## ADR-006 — Evaluate the existing Spherewright bridge before duplicating game actions

**Date:** 2026-09-23. **Source:** developer choice. **Status:** provisional.

An MIT-licensed bridge already exposes guarded, normal-mechanics game actions for a pinned DSP build. Evaluating its released capabilities on the owner's Windows installation may reach the iron experiment faster and safer than recreating placement from scratch. Keep this repository's health-only bootstrap isolated while compatibility is unknown; build the autonomous planner here once the usable action surface is confirmed.

**Rules out:** Duplicating complex write paths from source examples before checking the existing bridge and the installed game. It does not rule out a project-owned plugin if needed.

**Revisit if:** The owner's game version is incompatible, the release lacks required actions, or its safety/protocol model cannot meet the acceptance contract.
